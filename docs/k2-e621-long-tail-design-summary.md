# K2 视觉整理原则与 e621 目标覆盖设计总结

> 状态：仅设计记录，未实现。目标 tag 清单、总预算和保底数量仍待确认。
>
> 权威来源：[Krea 2 Technical Report](https://www.krea.ai/blog/krea-2-technical-report)。本地摘录缓存：[K2 数据整理缓存](references/krea-2-technical-report-data-curation-cache.md)。

## 定位与一句话结论

K2 更适合指导视觉/风格分布整理：本项目借鉴其 midtraining 做法，在当前 scope 的图像向量上先做层次聚类，并在需要压缩训练集时保留视觉长尾。e621 tag 是另一层用户约束，用于指定概念、核对覆盖和按唯一图片计数；不能从 K2 的视觉簇稀有度推导 e621 tag 配额。

因此，本设计不是“用 K2 平衡 e621 概念长尾”，而是“用 K2 整理视觉多样性，再用 e621 tag 检查用户指定目标”。

## K2 报告中实际描述的流程

K2 报告把下面几件事放在 `midtraining` 的数据整理流程中：

```text
当前 scope 的图像向量
  → FAISS hierarchical k-means
  → 按层次簇采样，保留 long-tail visual concepts
  → 查看每个簇质心附近的图片
  → VLM 给簇命名并在需要时标记
  → 人工审核被标记的簇并移除问题簇
  → 在剩余叶簇内计算 SigLIP 相似度做语义去重
```

报告没有公开固定的簇配额公式、阈值或具体实现参数，因此本项目不能把某个自定义公式写成“K2 官方算法”。
报告也没有规定聚类向量模型或本项目的 scope 划分方式；向量模型、scope 和配额属于项目配置。

报告另外描述了一条面向可按名称引用的已知实体覆盖流程：

```text
Wikipedia PageRank
  → Wikidata 过滤不可视觉化主题
  → 在 caption 中搜索概念
  → 优先采样稀有概念
  → 采样后再次检查概念是否被完全丢弃
```

这条流程依赖 caption。它不是“簇”的定义，也不能与没有 caption 的 e621 tag 覆盖直接等价。

## e621 数据中的对应关系

| 内容 | 作用 |
|---|---|
| 原始 e621 tag | 图片到概念的直接映射 |
| e621 tag 分类、Tag Wiki | 解释标签含义和使用边界 |
| tag alias | 把同义写法规范到一个 canonical tag |
| tag implication | 可作为推断关系统计，但必须和直接 tag 分开 |
| embedding 簇 | 描述视觉/语义表现的分区，不是标签分类 |
| 长尾采样 | 项目明确压缩预算时保留小型视觉簇；不等同于稀有 e621 tag 保护 |
| VLM | 看簇代表样本，命名或标记问题簇；不逐图替代 e621 tag |
| SigLIP 叶簇去重 | 找近重复候选，交给人工审核（项目安全门；K2 只公开相似度去重） |

簇不按 tag 建立：同一个 tag 可以跨多个簇，一个簇也可能包含多个 tag。一个簇的名称是审核解释，不是 k-means 自动产生的事实标签。

## 多 tag 重叠时怎样限制数据

**选择单位必须是唯一图片，而不是 tag 行。**

例如：

```text
图片 A：fox、blue_eyes、solo
图片 B：fox、blue_eyes
```

选中图片 A 后：

- 总图片数只增加 1；
- A 可以同时计入三个 tag 的覆盖统计；
- 不能把三个 tag 计数相加，得到“选了 3 张图”；
- 如果要求 `fox` 至少 100 张，必须有 100 张不同的图片带有 `fox`。

建议的预算逻辑：

1. 先设一个全局图片预算 `N`。
2. 只对用户明确指定的目标 tag 设置最低保留量；目标清单目前待定。
3. 在预算内优先满足 required 目标 tag，同时尽量选择来自不同视觉簇的图片。
4. 目标满足后的余量按视觉簇做多样性和长尾保留；不能因为 tag 稀有或常见就自动改变其目标优先级。
5. 每张图片只导出一次；tag 统计允许一张图片同时覆盖多个概念。
6. 导出前报告每个 tag 的 `selected_unique_images`、直接覆盖和推断覆盖，以及未满足的目标，不复制图片、不静默降低约束。

具体配额算法、稀有度权重和目标 tag 范围尚未确认，不能先写死。

## 推荐的项目流程（K2 视觉整理与 e621 目标约束分层）

```text
保留原始 tag，并规范化 alias
  → 对当前 scope 的全量图片生成向量（模型和版本由项目配置）
  → 在当前 scope 内建立 hierarchical k-means 簇（不按 tag 分簇）
  → 仅在启用压缩预算时按层次簇采样以保留视觉多样性（项目策略）
  → VLM 查看簇质心附近代表图并标记问题簇
  → 人工确认问题簇
  → 剩余叶簇内生成 SigLIP 近重复候选
  → 人工审核重复候选（项目安全门）
  → 按用户指定的 e621 tag 复验概念覆盖，并单独报告视觉簇覆盖
  → 生成可预览、可撤销的唯一图片导出快照
```

如果没有总量压力，可以跳过“长尾采样”；聚类不应仅因簇大小自动删除图片，问题簇和近重复仍按审核规则处理。

## 明确不做的事

- 不把 e621 tag 重新设计成另一套概念分类。
- 不把 K2 的视觉长尾直接解释成 e621 tag 长尾。
- 不从视觉簇大小、tag 频率或 tag 稀有度自动推导目标配额。
- 不把 Wikipedia/Wikidata/caption 检索流程伪装成 e621 的必要步骤。
- 不因为某个目标 tag 很常见，就自动把它当作应被压低的“头部概念”。
- 不让 VLM 逐张重打 tag。
- 不用未校准的相似度阈值自动排除图片。
- 不把 SAE 原始特征当作已解释的伪影或长尾标签。

## 待用户确认的参数

- 哪些 e621 tag 是 LoRA 的目标概念；
- 每个目标 tag 的最低数量，是否需要最高数量；
- 总图片预算 `N`；
- 采样 scope 是单个目录、多个目录还是全局；
- VLM、SigLIP 版本和审核标准；
- 是否把 implication 计入覆盖，以及如何显示直接/推断差异；是否统计传递性 implication；
- alias/implication 规则的快照版本和生效时间；
- 人工决定、required 目标、簇多样性和非目标软上限之间的优先级。
